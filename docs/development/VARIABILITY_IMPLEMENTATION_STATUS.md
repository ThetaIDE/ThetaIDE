# Local variability execution

Experiments may opt in with `variability.training_runs` and `variability.parallel_runs`. Each launch draws that many fresh training seeds, and an evaluation seed when every method supports one, as [launch seeds](../reference/LAUNCHES.md#seeds) describes. An explicit `variability.training_seeds` list (and `variability.evaluation_seed`) reproduces a recorded run; the editor offers it as the alternate form. The editor also surfaces the existing `eval_episodes` value. An absent variability section keeps the existing launch path.

Each launch has a UUID manifest under `results/executions/<group>/<experiment>/<execution-id>/manifest.json`. Results use a unique run folder below the experiment ID (or reuse the unique IDE/cluster launch folder); methods and seeds occupy agent/version subdirectories. See the [saved result layout](../reference/RESULT_STORAGE.md). The manifest records the plan, runner capabilities, expected artifact paths and queued/running/completed/failed states. Training seed is passed as `seed` and, for methods with agents, `agent.seed`. Custom runners must honor the provided experiment ID and seed; the launcher cannot guarantee their isolation or seeding.

The Lightning online-RL callback and SB3 runner record per-episode evaluation rewards in the run's `evaluation_events.jsonl`. Both use a separate evaluation environment. Events record the in-memory policy's step, evaluation seed passed, action protocol and episode outcomes; they do not claim that a checkpoint was saved at that step. The Lightning vector environment uses `(evaluation_seed + event_index) modulo (2^32 - worker_count)`; SB3 uses `(evaluation_seed + event_index) modulo (2^32 - 1)`. The launch draws the evaluation seed when the config leaves it open and every method supports it; otherwise each runner uses its default. Environment plugins control worker and subsequent episode seeding, and deterministic GPU behavior is not guaranteed.

The Results browser shows each replicate as a version of its method; select several versions and set the Monitors combine control to Mean ± std or Mean ± SEM to draw one mean curve with a band. The execution data interface (`src/app/services/executions.py`) reads a manifest's statuses, per-replicate evaluation events and the mean of per-run episode means; its grid is the union of observed steps, interpolated only within each run's observed range.

Tuning and repetitions are mutually exclusive. Workflow and recovery launches are rejected, and Slurm parity is outside the current implementation. Stopping a job through the IDE marks its unfinished replicates cancelled; abrupt termination outside the IDE can leave statuses stale. Retry and resume remain unimplemented. Individual legacy plotters can still operate on individual runs; the repeated execution path does not automatically invoke them. Plotters that write to a user-configured shared output path may need their own isolation policy.
