# Local variability execution

Experiments may opt in with `variability.training_runs`, `variability.starting_seed`, and `variability.parallel_runs`. The editor exposes training count and starting seed; the optional explicit `variability.training_seeds` list is an alternate advanced form. Configure one form at a time. The editor also surfaces the existing `eval_episodes` value. An optional `variability.evaluation_seed` requests a reproducible evaluation seed protocol when the selected runner supports it. An absent variability section keeps the existing launch path.

Each launch has a UUID manifest under `results/executions/<group>/<experiment>/<execution-id>/manifest.json`. Results use a unique run folder below the experiment ID (or reuse the unique IDE/cluster launch folder); methods and seeds occupy agent/version subdirectories. See the [saved result layout](../reference/RESULT_STORAGE.md). The manifest records the plan, runner capabilities, expected artifact paths and queued/running/completed/failed states. Training seed is passed as `seed` and, for methods with agents, `agent.seed`. Custom runners must honor the provided experiment ID and seed; the launcher cannot guarantee their isolation or seeding.

The Lightning online-RL callback and SB3 runner record per-episode evaluation rewards in the run's `evaluation_events.jsonl`. Both use a separate evaluation environment. Events record the in-memory policy's step, evaluation seed passed, action protocol and episode outcomes; they do not claim that a checkpoint was saved at that step. The Lightning vector environment uses `(evaluation_seed + event_index) modulo (2^32 - worker_count)`; SB3 uses `(evaluation_seed + event_index) modulo (2^32 - 1)`. Without an explicit seed each runner uses its default. Environment plugins control worker and subsequent episode seeding, and deterministic GPU behavior is not guaranteed.

The Results browser's Executions tab lists statuses and individual episode events, opens individual runs, and plots the mean of per-run episode means for completed runs. Its grid is the union of observed steps; values are interpolated only within each run's observed range. Counts are displayed for every step, and the sample standard deviation band is suppressed when the grid includes fewer than two contributing runs. Episode rewards are shown separately for a selected model and evaluation event. The execution data interface is versioned and includes a legacy adapter that does not invent episode data.

Tuning and repetitions are mutually exclusive. Workflow and recovery launches are rejected, and Slurm parity is outside the current implementation. Stopping a job through the IDE marks its unfinished replicates cancelled; abrupt termination outside the IDE can leave statuses stale. Retry and resume remain unimplemented. Individual legacy plotters can still operate on individual runs; the repeated execution path does not automatically invoke them. Plotters that write to a user-configured shared output path may need their own isolation policy.
