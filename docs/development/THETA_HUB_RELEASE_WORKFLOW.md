# Releasing a component to Theta Hub

Use this procedure when a request includes publishing a component to the production hub. A component change, an IDE change, and a published hub release are separate deliverables: a new package cannot update code already shipped in the IDE. If a request only asks for local changes, do not publish as an assumed side effect.

## Prepare the release

1. Inspect the current hub remote, branch, status, and the latest production commit. `../theta-hub` may be behind production and may contain unrelated user changes. Preserve them; a fresh temporary clone of the current remote is useful for an isolated release. Check the actual remote and workflows rather than assuming the repository URL or deployment process is unchanged.
2. Identify the authoritative source for the component and compare it with the latest published archive. Preserve existing behavior and user changes. Choose a new version greater than the current live version; do not overwrite an existing release archive. Keep the package manifest, archive name, registry version, release URL, and hash consistent.
3. Check the component's config defaults, runtime consumers, and manifest schema together. For UI issues, inspect the IDE renderer as well: a manifest cannot fix unsupported or incorrect core rendering. Describe any IDE change and how users will obtain it separately. For multiple config profiles, provide profile-specific schemas using `x-theta-config-schemas` where appropriate. Avoid inventing bounds, choices, or types that runtime behavior does not support.
4. Build the archive with the expected layout, including `.theta_component.json`, required source files, and config profiles. Check its contents, manifest, version, and SHA-256; ensure its registry URL points to the exact published archive. Retain existing release entries unless there is a specific reason to change them. Run relevant component and IDE tests, and report missing dependencies or skipped coverage.

## Publish and verify

1. Update the component registry manifest in the hub clone and validate it with `python scripts/validate_manifest.py`. Run `python scripts/build_index.py` from the hub repository. Inspect the generated diff; the build can update timestamps across feeds. Commit the intended package, registry manifest, and generated `dist` feeds needed by clients together, without including unrelated changes. The current IDE default reads the repository's `dist/index.json`, not only the GitHub Pages deployment artifact. A successful Pages workflow alone therefore does not prove the IDE can see a release.
2. When production publication is authorized, push the release using the required environment permissions. Do not force-push or overwrite other releases. If the remote advanced, reconcile against its new state without discarding unrelated work. Check the deployment workflow's result when applicable.
3. Fetch the **exact URL configured by the target client** (see `DEFAULT_REGISTRY_URL` and fallback behavior in `frontend/hub/client.py`), and verify the response contains the intended component version, release URL, and hash. Fetch the archive from that URL and verify its SHA-256 and manifest. Check the Pages feed too if clients use it. If a feed is stale, distinguish deployment failure from CDN or client caching; a commit-specific URL can establish what was actually pushed, but does not prove the client's mutable URL is current.
4. When feasible, exercise a fresh client fetch and the install/update path in an isolated workspace, without replacing a user's installed component or configuration. Verify the installed version and relevant packaged files. The Hub's Refresh action requests a forced refresh; a running IDE must be restarted to pick up changes to the IDE client itself. Account for network fallback to an older feed or local cache when diagnosing a missing release.

Report the published version, the actual feed and package verification, deployment status, and any remaining limitation. Do not claim the release is visible or that an IDE fix is live based solely on a successful push or workflow run. The existing [local component development workflow](../guides/COMPONENT_DEVELOPMENT.md) is separate: copying, editing and exporting a local component do not publish a release or replace these production checks.
